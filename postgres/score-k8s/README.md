## For `10-cnpg-postgres.provisioners.yaml`

Provisions a dedicated [CloudNativePG](https://cloudnative-pg.io/) `Cluster` per `postgres` resource, instead of the single-replica `StatefulSet` that the built-in `score-k8s` provisioner generates. The operator then owns the storage, the failover, the read/write endpoints and, if you configure it, the backups.

Two manifests are generated:

- a `kubernetes.io/basic-auth` `Secret` holding the application user and a generated 16-character password,
- a `postgresql.cnpg.io/v1` `Cluster` bootstrapped with `initdb`, using that Secret as the database owner.

The credentials are generated by the provisioner rather than by the operator (which would create its own `<cluster>-app` Secret with a password we can't read at generate time). They are kept in the score-k8s state file, so the outputs stay stable across `score-k8s generate` runs.

The outputs are the same as the built-in `postgres` provisioner, so this is a drop-in replacement:

- `host` - the `<cluster>-rw` Service, which always points at the current primary.
- `port` - `5432`.
- `name`, `database` - the database name.
- `username` - the database owner.
- `password` - injected as a `secretKeyRef`, never rendered in plain text in the manifests of the workload.

Params, all optional:

| Param | Default | Description |
| ----- | ------- | ----------- |
| `database`   | `app`   | Name of the database created at bootstrap. |
| `username`   | `app`   | Owner of that database. |
| `instances`  | `1`     | Number of PostgreSQL instances. Use `3` for a primary and two hot standbys. |
| `storage`    | `1Gi`   | Size of the volume of each instance. |
| `imageName`  | (operator default) | PostgreSQL image, for example `ghcr.io/cloudnative-pg/postgresql:17.2`, to pin the major version. |

A couple of things worth knowing:

- Only the read-write endpoint is exposed as an output. If a workload needs to send read-only queries to the standbys, point it at the `<cluster>-ro` Service that the operator creates alongside it.
- Bootstrapping a cluster takes a few seconds, and the workload is deployed at the same time. Applications are expected to retry their first connections.
- `params.database` and `params.username` only apply when the cluster is bootstrapped. Changing them afterwards won't rename anything in an existing cluster.

Prerequisites:
- Have the CloudNativePG operator installed in the target cluster, it owns the `Cluster` CRD generated here:
    ```bash
    kubectl apply --server-side -f \
      https://raw.githubusercontent.com/cloudnative-pg/cloudnative-pg/release-1.25/releases/cnpg-1.25.4.yaml
    ```
    See the [installation guide](https://cloudnative-pg.io/documentation/current/installation_upgrade/) for the Helm chart and the up-to-date versions.
- Have access to a cluster with a default `StorageClass`.
    - If you don't have one, you can deploy a `Kind` cluster locally by running this script: `.scripts/setup-kind-cluster.sh`.
